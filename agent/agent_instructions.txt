PER-DIAGRAM METHOD (run in full for L0 and for every child diagram)
A Model. Extract with IDs: TB# trust boundaries (left to right: most untrusted first, build/admin planes last); E# external entities, P# processes, D# data stores, each in one boundary; F# flows: from, to, data carried, protocol, authentication. Implied but not stated: "assumed": true.
B Frameworks. STRIDE per element always. LINDDUN whenever personal data is collected, stored, shared or inferred. OWASP Top 10:2025 for web apps, API Security 2023 for APIs, LLM 2026 for any LLM/RAG use, Agentic 2026 for agents/tools/MCP/memory, CI/CD Top 10 for pipelines/build. State which apply to this diagram and why.
C Threats. Work element by element, then every flow that crosses a trust boundary. Use the TM-01 threat statement format. Score likelihood (1-5) x impact (1-5) with the TM-01 rubric; Critical 20-25, High 12-19, Medium 6-11, Low 1-5. Each threat: one target, at least one framework ID (LINDDUN code for privacy threats, e.g. LINDDUN DD), refs, a specific control. Gaps that block assessment are threats with a "gap" ref. Never invent components.

DECOMPOSITION LOOP
1 Run the method on L0 (max 20 elements).
2 For each process, apply the TM-01 decomposition test: the documents describe 3+ internal components AND it has a Critical/High threat, crosses 2+ boundaries or holds sensitive data. If yes, create L1-P# (then L2-P#.#): own IDs prefixed with the parent (P3.1, P3.D1, P3.F1); neighbours from the level above as context elements with the same IDs; child flows set parent to the flow they detail. Run the full per-diagram method A-C on it; child threats that detail a parent threat set refines.
3 Repeat for the new processes. Stop when the test fails, the documents give no more detail, or at L2 (L3 only if asked). Max 15 elements per child incl. context. Record stop_reason on every diagram.
4 Review: every Critical/High threat on a decomposed element is refined in its child and addressed by an improvement; every gap has a question; no duplicate threats across levels (use related).
5 Attack paths AP# (3-6 key ones): realistic chains from an external entity (entry E#) to a business objective, each step an existing threat at any level (L0/L1/L2) plus the attacker action. Prefer paths that cross trust boundaries and levels and end in Critical impact. Score likelihood x impact for the whole chain.
6 Architecture improvements R# (P1/P2/P3), each listing the threats it addresses and refs; every attack path must be broken by at least one. Questions Q# linked to threats and refs.
7 Numbering: T1..Tn by level, diagram, severity, element order. Keep IDs stable in later turns; new items take the next number.
